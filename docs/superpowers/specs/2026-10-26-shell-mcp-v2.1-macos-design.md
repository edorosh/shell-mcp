# shell-mcp v2.1 — macOS Hosts Design

Date: 2026-10-26 · Milestone: [ROADMAP v2.1](../../../ROADMAP.md#v21-macos-hosts)
· Builds on: [v1 design](2026-10-25-shell-mcp-design.md),
[v2 npm design](2026-10-25-shell-mcp-v2-npm-design.md), [product spec](../../product-spec.md)
· Spike: [v2.1 macOS spike results](v2.1-macos-spike-results.md)

Server behavior is unchanged. This document records what it takes to make
Apple Silicon macOS a supported host for `@edorosh/shell-mcp`: CI, one
diagnostic for unsupported Macs, docs and a release. Requirement IDs (N6, C9,
...) refer to the product spec. Linux hosts stay in ROADMAP v4.

## 0. Goal and success criteria

- **For:** a developer on an Apple Silicon Mac who uses Claude Code or VS Code
  Copilot and wants their agent's shell commands to run in a microsandbox
  Linux sandbox. They should need only Node; no clone, no build, no separate
  `msb` install.
- **Done when:** on the maintainer's Apple Silicon Mac, following the docs with
  the published 1.1.0 package gives a passing `--check`, the acceptance suite
  passes 12 of 12, and in one Claude Code and one Copilot session `uname -a`
  through the agent reports Linux with the built-in shell turned off.
  The spike already showed this for 1.0.2 (see §3); the release check repeats
  it with 1.1.0.
- **Not a goal:** Intel Macs, any change to how the server behaves once
  running, Linux hosts, Homebrew.

## 2. What is already host-neutral

Read from the code on main (2c6c810) before the spike:

- `PathMapper` (`src/paths.ts`) and `parseConfig` (`src/config.ts`) use
  `path.posix` on every platform but `win32`, so POSIX host roots such as
  `/Users/<you>/dev/myproj` already work.
- The shell runs in the Linux guest on every host; `src/wrap.ts` builds
  POSIX shell text only.
- The `--check` mount step folds case only on `win32` (`src/check.ts`). On
  macOS the guest returns names exactly as stored, so an exact comparison is
  correct (spike Step 3).
- Error mapping in `src/backend/microsandbox.ts` is by SDK error code. The
  Windows-only `GenericFailure` case does not occur on macOS, where the SDK
  reports `sandboxNotRunning` for a held connection (spike §Held connection).

## 3. Stage A: spike on a real Mac

Done 2026-10-26; full record in [v2.1-macos-spike-results.md](v2.1-macos-spike-results.md).
The steps were: machine facts; create a sandbox with the bundled `msb`;
`--check` with the published package; mount edge cases (case, NFC/NFD names,
symlinked host root); `spike/sdk-check.mjs` with a stopped sandbox;
`spike/stop-check.mjs`; the integration suite; Claude Code; Copilot with the
`deny-shell.sh` hook.

Outcome: every step passed with 1.0.2. Findings that shape Stage B:

1. `msb` rejects bind mounts through a symlink and names the resolved path.
2. The bundled `msb` is not on `PATH`; the integration suite and
   `stop-check.mjs` need it there.
3. Guest images must have an arm64 variant.
4. The guest sees the host's case-insensitive file system.
5. zsh copy-paste blocks must not contain `#` comments.

## 4. Stage B: changes

### 4.1 CI (`.github/workflows/ci.yml`)

- Add `macos-latest` (GitHub's arm64 runner) to the `test` matrix next to
  `ubuntu-latest` and `windows-latest`: typecheck, build, unit tests.
- Turn the `pack` job into a matrix over `windows-latest` and `macos-latest`,
  so `scripts/check-pack.mjs` starts the packed bin on macOS too.
- The integration suite stays manual: hosted runners cannot start
  microsandbox VMs.
- The release workflow is unchanged (it publishes one platform-neutral
  tarball).

### 4.2 Unsupported-Mac diagnostic

When `import("microsandbox")` or `resolveRuntime()` fails and
`process.platform === "darwin"` and `process.arch === "x64"`, the message
becomes:

```
<SDK error>; macOS needs Apple Silicon and an arm64 Node (this Node is x64: an Intel Mac, or Node running under Rosetta)
```

instead of the generic `reinstall shell-mcp without --omit=optional …` hint.
Every other platform keeps today's hint.

- One pure helper (for example `nativeHint(platform, arch)` in
  `src/runtime.ts`) used by both the `--check` native step (`src/check.ts`)
  and the runtime hint, so the two messages cannot drift.
- Platform and arch are passed in (defaulting to `process.*`), as `parseConfig`
  already does for `platform`, so unit tests cover darwin/x64,
  darwin/arm64 and win32/x64 without a Mac.
- Serving behavior is unchanged: the message goes to stderr (C9) and the
  server keeps its current failure behavior.

### 4.3 package.json

- Add the `macos` keyword. No `os`/`cpu` fields (§1).
- Version 1.1.0 at release time, with all doc pins bumped per
  [releasing.md](../../releasing.md).

### 4.4 Docs

Follow the AGENTS.md rule: README stays minimal; detail goes in `docs/`.

- **README:** "Windows hosts only" becomes "Windows and Apple Silicon macOS
  hosts"; quick start shows a macOS line next to the PowerShell one.
- **docs/sandbox.md:** a macOS section: create with
  `npx -y -p microsandbox@0.7.11 msb create ubuntu:24.04 --name myproj --mount-dir "$(cd ~/dev/myproj && pwd -P):/workspace"`;
  why `pwd -P` (the symlink error, quoted); images need arm64; the guest
  inherits macOS case-insensitivity.
- **docs/clients.md:** macOS `.mcp.json` and `.vscode/mcp.json` examples with
  `/Users/<you>/dev/myproj`; the `deny-shell.sh` hook marked verified on macOS
  (2026-10-26).
- **docs/troubleshooting.md:** "bind mount host path … goes through symlink";
  "native module failed on an Intel Mac or under Rosetta" (check
  `node -p process.arch`).
- **docs/development.md and AGENTS.md:** the integration suite runs on Windows
  or an Apple Silicon Mac; on macOS put the bundled `msb` on `PATH` first; CI
  runs on Ubuntu, Windows and macOS.
- **docs/known-issues.md:** client support table: Claude Code and Copilot
  verified on macOS; `deny-shell.sh` verified on macOS, still untested on
  Linux.
- **docs/product-spec.md:** N6 narrows to Linux hosts; host definition gains
  Apple Silicon macOS.
- **CHANGELOG.md:** `[Unreleased]`: "Added: Apple Silicon macOS hosts."
- **ROADMAP.md:** v2.1 status to done at release.
- Placeholders: `/Users/<you>/…`, never a real user name or volume name. No
  inline `#` comments in zsh blocks.

## 5. Error handling

No new runtime errors. The one changed message is §4.2. The symlink failure
comes from `msb create`, before shell-mcp is involved, so it is a docs entry,
not code.

## 6. Testing

- Unit: the §4.2 helper for darwin/x64 (Apple Silicon message), darwin/arm64
  and win32/x64 (generic hint), and the `--check` native step using it.
- CI: the new macOS jobs must be green before merge.
- Manual, on the Mac, with the released 1.1.0 from a folder outside any clone:
  `--version`, `--check`, the integration suite (12 of 12), Claude Code
  `uname -a`, Copilot with the hook. Record the result in the v2.1 plan.

## 7. Out of scope

- Intel Macs: revisit if the SDK ships a `darwin-x64` package.
- Resolving symlinks in `--host-root` or translating both symlinked and
  resolved paths: not needed, because the `shell` tool takes no host cwd and
  both forms are valid host paths for the client's own file tools.
- Running the integration suite in CI.
- Linux hosts (v4), sandbox creation from config (v3), Homebrew.
