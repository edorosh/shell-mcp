# shell-mcp v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A host-side stdio MCP server exposing `shell`, `shell_output`, `shell_kill` and `shell_list`, which run every command inside one pre-existing microsandbox sandbox.

**Architecture:** Pure modules (config, paths, output, wrap, jobs) plus a `ShellService` that implements the four tools against a `Backend` interface. `tools.ts` registers the service with the MCP SDK. `backend/microsandbox.ts` implements `Backend` with the microsandbox TypeScript SDK. Everything except that backend is tested on any machine with a fake backend. The backend is tested by an integration suite on a host with `msb`.

**Tech Stack:** TypeScript (ESM, `"module": "NodeNext"`), Node ≥ 22 (the `microsandbox` SDK's `engines` floor), `@modelcontextprotocol/sdk` 1.x, `zod` (the major the SDK's peer dependency names), `microsandbox` (exact pin), `vitest`.

**Spec:** [docs/product-spec.md](../../product-spec.md) (behavior, requirement IDs) and [docs/superpowers/specs/2026-10-25-shell-mcp-design.md](../specs/2026-10-25-shell-mcp-design.md) (implementation decisions). Read both before starting.

## Global Constraints

- Node ≥ 22. ESM only. `package.json` `"bin": { "shell-mcp": "dist/index.js" }`, `"private": true`.
- **The unscoped npm name `shell-mcp` is taken by an unrelated package.** Never write `npx shell-mcp` anywhere (README, examples, design): it would run a stranger's code on the host (A1). v1 is not published; client configs run `node <path>\dist\index.js`. If it is published later, it goes under a scope the user owns.
- Tool names exactly `shell`, `shell_output`, `shell_kill`, `shell_list`. `shell` params exactly `command`, `description`, `timeout_ms`, `run_in_background`. The job tools take `job_id`.
- Defaults: `default-timeout` 120 s, `max-timeout` 600 s, `max-output` 30000 characters, rewriting on, shell `bash`.
- Nothing but MCP protocol on stdout. All diagnostics go to stderr via `console.error` (C9).
- The server never runs agent commands on the host. `src/` MUST NOT import `child_process` (X1, X2). Tests may use it. `test/no-host-exec.test.ts` (Task 2) enforces this.
- The server never creates, starts, stops or removes sandboxes (B3).
- Pin `microsandbox` to an exact version (no `^`). Record the version tested against `msb` in README.
- Host: Windows only in v1 (spec G4, N6). Host-path code still takes a `platform` parameter and uses `path.win32`/`path.posix` explicitly. Never use bare `path` for host roots. Unit tests use `"win32"` and run on any OS. Linux-mapper tests stay as cheap regression guards, but no Linux/macOS host verification is done.
- Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

**Environment note:** The development sandbox for this plan has Node but no `msb` and no KVM. Tasks 1 and 9, and the manual check in Task 10, run on the user's host. All other tasks run and pass anywhere.

## Review Focus

1. **Windows host root written with `/` or different letter case** in config (`c:/Users/eugen/proj` against `C:\Users\eugen\proj`). The mapping still works, and output shows the configured form. Pinned in Task 3.
2. **Commands that fight the wrapper:** containing `'`, a trailing `# comment`, an unterminated here-doc, `exit 7` mid-script, or a `cd` inside a subshell. Exit code and cwd stay correct. Pinned in Task 4 by executing wrapped scripts with local bash.
3. **Command output that forges a marker** (`__SHELLMCP_CWD_wrongnonce__/etc`) passes through untouched and doesn't move the cwd. Pinned in Task 4.
4. **Multi-byte UTF-8 split across stream chunks** decodes without replacement characters, including when a stderr chunk arrives between the two halves of a stdout character, and when a character is split across two job log entries. Pinned in Task 5 (decoder) and Task 8 (one decoder per stream and per job).
5. **A background job that prints far more than `max-output`** is returned in successive `shell_output` pages with "more output pending", and nothing is lost. Pinned in Task 7.

  ```ts
  // backend/types.ts — design §5, without listJobs
  // droppedChars: characters the backend discarded from the middle to cap memory.
  // The service passes it to truncateMiddle so the omitted count is exact.
  export interface RunResult { output: string; exitCode: number | null; timedOut: boolean; droppedChars: number }
  export type JobState = "running" | "exited" | "lost" | "unknown"
  // error: set when the job failed to launch (SDK state "failed")
  export interface JobStatus { state: JobState; exitCode?: number; error?: string }
  export interface Backend {
    run(script: string, opts: { timeoutMs: number; signal?: AbortSignal }): Promise<RunResult>;
    startJob(script: string): Promise<{ id: string }>;
    readJob(id: string, cursor?: string): Promise<{ text: string; cursor?: string; gap: boolean }>;
    jobStatus(id: string): Promise<JobStatus>;
    killJob(id: string, waitMs: number): Promise<{ confirmed: boolean; status: JobStatus }>;
  }
  export type BackendErrorKind = "not_found" | "not_running" | "unreachable" | "not_started" | "outcome_unknown"
  export class BackendError extends Error { constructor(kind: BackendErrorKind, message: string) ; readonly kind: BackendErrorKind }
  // jobs.ts
  export interface JobRecord { id: string; command: string; startedAt: Date; cursor?: string; pending: string; killedByUs: boolean }
  export class JobRegistry { add(id: string, command: string): JobRecord; get(id: string): JobRecord | undefined; list(): JobRecord[] }
  export function shortenCommand(cmd: string, max = 80): string   // first line, "…" if cut
  // service.ts
  export interface ToolResult { text: string; isError: boolean }
  export interface CallContext { signal?: AbortSignal; onProgress?: (elapsedSec: number) => void }
  export class ShellService {
    constructor(cfg: Config, backend: Backend, deps?: { nonce?: string; progressIntervalMs?: number; now?: () => Date })
    shell(args: { command: string; description?: string; timeout_ms?: number; run_in_background?: boolean }, ctx?: CallContext): Promise<ToolResult>
    readonly cwd: string   // guest path, for tests
  }
  // descriptions.ts
  export function describeTools(cfg: Config): { shell: string; shell_output: string; shell_kill: string; shell_list: string }
  ```

- [ ] **Step 1: Write the failing tests** in `test/service.jobs.test.ts`, with a fake that also scripts `readJob`/`jobStatus`/`killJob`:
  - Unknown `job_id` → `isError true` with `unknown job` for `output` and `kill` alike (O4, K4). The backend is not called.
  - `output`: the first read passes `cursor undefined` and the second passes the cursor returned first (O1). The text starts with `status: running`, and job output is path-rewritten.
  - Paging (Review Focus 5): `maxOutput 100` and a read returning 250 chars give three successive `output` calls. The backend is read once, and the leftover is served from `pending`.

### Verified on a real host (Windows, `msb` 0.7.11, SDK 0.7.11)
Spike results are in [spike-results.md](../specs/spike-results.md). The acceptance suite (`test/integration.test.ts`, spec §13 criteria 1–12) passes 12/12 with `SHELL_MCP_IT_ALLOW_STOP=1`.

### Deviations from this plan
- **Truncation example (Task 5):** the plan expects `[... 1900 characters omitted ...]` at `max=100`, which cannot fit in 100 characters. The length bound wins; the marker count equals what was actually removed.
- **Criteria 3 and 12 (Task 9):** verified with `--no-rewrite-output-paths`. With default rewriting, `pwd` prints the host form while the criterion says the guest path is reported. Noted in `docs/product-spec.md`.
- **Criterion 12 waits for the mount:** the test polls until the guest no longer sees the deleted directory (see the first known issue below).
- **`Utf8Accumulator`** gained `finish()` (end-of-stream flush) and `drain()` (take decoded text so the backend memory cap holds). `text()` does not flush.
- **`shell_output` reads job status before the log** and also reads when at most one page is pending, so a job's final output is not lost. Reads of one job are serialized (concurrent calls would replay output).
- **Timeouts:** shell-mcp kills the process itself at the deadline + 500 ms and waits 2.5 s for the exit, returning the captured output either way. The SDK's own deadline kill normally wins (exit code -1, confirmed by the spike).
- **Error wording:** any failure while looking up or connecting to the sandbox, and the SDK's `GenericFailure` on a held connection after `msb stop`, map to "unreachable", which names the sandbox and `msb start <name>`.
- **Commit trailer** is `Claude Sonnet 5.5`, not the Opus line in Global Constraints (the model that did the work).

### Known issues (not fixed)

Fixed after the first write-up: the reset marker now carries its own leading newline (the note could be lost, and the raw marker could leak, when a command's output had no trailing newline and arrived first), and a stream that ends after shell-mcp's own deadline kill now returns `timedOut` with the captured output instead of `outcome_unknown`.

1. **Host-mount lag (~5 s).** After the host deletes the current directory, the guest keeps resolving it for about 5 s (measured 5.25 s), so the next `shell` calls run there instead of resetting to the workspace root. The parent directory listing is fresh at that moment, so a wrapper check against the parent's listing is a candidate fix; it needs its own tests and a real-sandbox check. Documented in the README.
2. **Unexercised error paths:** `output_gap` (job log retention), `launch_unconfirmed`, and `job_not_found` for a well-formed missing id were not triggered on a real host. A retention gap before the first read of a job cannot be detected.
3. **Client timeouts (design §2 risk 5): resolved.** Copilot in VS Code held foreground calls up to 600 s without a setting change. Claude Code (no `MCP_TOOL_TIMEOUT`) moves calls over 120 s to a background task and still delivers the result; that task dies if the session exits. Neither client showed progress for these calls. The sandbox's `sleep` overruns by about 3%, so a command sized to the exact deadline times out (README, Client timeouts).

### Accepted minors (from task reviews)
- Config: a Windows host root like `\foo` (no drive) counts as absolute; `guestRoot` is only trailing-slash stripped (the path mapper normalizes its own copy); the `no-host-exec` test resolves `src` relative to the cwd; `tsconfig.json` does not include `test/`.
- A user `trap ... EXIT` or `exec` in a command disables cwd tracking for that call; a newline in the cwd path is unsupported.
- `shell_list` fails entirely if `jobStatus` fails for one job; the 100-character page bound counts the output body only, not the `status:` header.
- A job killed by SIGTERM that exits 0 is reported as exited, not killed; the registry and decoder maps grow over a session; a killed process reports exit code -1, not 128+N.
- Unit-test gaps: tiny `max-output` combined with `alreadyOmitted` in truncation, and non-integer `timeout_ms`.
